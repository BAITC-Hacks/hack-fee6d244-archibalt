# Визуализация желаемого результата через GPT Image API

23.09.2026, Астана. Прямой запрос Ильяса: учитывать генерацию визуализации ТЗ, которое хочет заказчик, через GPT Image API. Предложенные решения из `product-scope-closure-2026-09-23.md` приняты. Здесь описаны продуктовый сценарий, предложение интеграции и приёмка. API ещё не подключён этой сессией; реальные генерация, стоимость и доступ к модели не проверены.

## Зачем

После понимания боли и выбора первого результата показать человеку наглядный образ того, что он получит. Помочь заметить расхождения до публикации заказа. Работает в существующем диалоге, без отдельного обязательного экрана.

## Путь заказчика

1. Агент использует уже известные сведения: бизнес, пользователи, нынешний процесс, боль, выбранный результат и ограничения. При готовом ТЗ извлекает их из него и задаёт только уместные вопросы по пробелам, соблюдая обязательные ≥3 вопроса в сценарии ТЗ.
2. После выбора результата в чат приходит предложение «Покажу, как это может выглядеть» с действием **«Показать пример»**. Для первой версии создаётся один концепт. Повторная генерация — по явному действию/сообщению пользователя, не после каждой реплики.
3. Визуальный артефакт появляется в той же переписке. Для продукта — пример ключевого экрана; для автоматизации — наглядная схема изменённого процесса; для визуальной задачи — пример результата. Выбирается один подходящий тип по контексту, без дополнительной анкеты о стиле.
4. Под изображением — короткое объяснение, какая боль решается, и действия **«Подходит»**, **«Изменить»**, **«Продолжить без картинки»**. Подпись «Пример будущего результата». Существенные данные, условия и критерии остаются обычным редактируемым текстом рядом.
5. Пользователь может написать «оплаты хочу видеть по ученикам». Агент извлекает конкретное уточнение, показывает его в тексте и обновляет концепт. Изменения внешнего вида не создают новые функциональные обязательства. Противоречие с уже подтверждённым требованием выносится на уточнение.
6. «Подходит» выбирает изображение для карточки заказа. Публикация остаётся отдельным действием над видимой карточкой и выбранной иллюстрацией. Команда видит текст, критерии приёмки и согласованный концепт вместе.

Генерация необязательна для публикации и работает в фоне: разговор и карточка доступны во время ожидания. Статусы простые: «Готовлю пример», «Готово», «Не получилось — повторить». Не показывать выдуманный процент выполнения.

## Пример для языкового центра

Известно: учёт разрознен между Excel и WhatsApp; теряются посещения, оплаты и домашние задания; участвуют преподаватели и администраторы. Предложенный первый результат — обзор одной группы.

Сообщение агента: «Покажу пример обзора группы, где рядом видны посещения, оплаты и домашние задания. Так будет проще уточнить, что вам нужно».

Изображение: один спокойный, читабельный экран; выбранная группа; условные строки «Ученик А», «Ученик Б»; три согласованных вида сведений. Демонстрационные записи обозначены как примеры. Реальные суммы, имена, проценты эффективности, сроки и доступы к источникам не выдумываются. График прибыли, CRM, AI-репетитор и другие не выбранные модули не добавляются для украшения.

Возможная правка: «Нужно видеть оплаты по каждому ученику и отдельно неоплаченные». Ожидаемый результат обработки: соответствующее требование появляется в редактируемом тексте, после чего обновляется визуальный пример; прежняя версия остаётся доступна до готовности новой.

## Связь картинки, текста и рейтинга

- Источник требований — текст задачи и явные уточнения пользователя. Детали, случайно нарисованные моделью, не извлекаются обратно как согласованное ТЗ.
- Изображение привязано к снимку исходных полей/выбранного результата. Если содержательные поля меняются, показывать «Пример нужно обновить». Поздно завершившаяся старая генерация не заменяет более новую выбранную версию.
- Красивое изображение само не приносит баллов готовности задачи. Баллы начисляются по правилам `TASK.md` за подтверждённые сведения. Уточнение, появившееся благодаря картинке, может улучшить рейтинг после подтверждения текста.
- Поддержать чтение без картинки: подпись и текстовое описание существенного содержания. Не прятать точные критерии в растровом тексте.
- В запрос модели передаётся короткое описание задачи с необходимым контекстом и выбранными ограничениями. Не отправлять всю историю клиента, контакты, секреты или нерелевантные вложения. Для демонстрации использовать обезличенные данные.

## Предложение технической интеграции для владельца API

Официальный [Image generation guide](https://developers.openai.com/api/docs/guides/image-generation) проверен 23.09.2026. Image API поддерживает генерацию и редактирование; Responses API поддерживает последовательные правки изображения в разговоре. Для текущего MVP можно оставить существующий текстовый диалог и подключить отдельный серверный Image API: `POST /v1/images/generations`, затем `POST /v1/images/edits` с предыдущим изображением. Перевод всего диалога на другой API не требуется.

Модель и качество задаются отдельной конфигурацией `OPENAI_IMAGE_MODEL`/`OPENAI_IMAGE_QUALITY`; доступ конкретного проекта необходимо проверить реальным вызовом. Базовый вариант по локальному Imagegen workflow — `gpt-image-2`, `1536x1024`, `medium`, одно изображение. Официальная документация также описывает новые модели GPT Image 2.5; выбор другой модели должен быть явным. Внутренний timeout клиента вопросов сейчас 10 секунд (`internal/ai/openai.go`), его нельзя переносить на изображения: руководство предупреждает, что сложная генерация может занимать до двух минут.

Предлагаемый контракт приложения, который владелец согласует с текущими моделями данных:

- `POST /api/tasks/{taskId}/visuals` — запустить генерацию или правку; вход: снимок/хеш задачи, выбранный результат, необязательные `previous_visual_id` и `instruction`, ключ защиты от повторного нажатия. Ответ `202`: ID и статус задания.
- `GET /api/tasks/{taskId}/visuals/{visualId}` — статус, версия исходного ТЗ, описание, ссылка на готовое изображение или понятная ошибка.
- Явное действие выбора готового изображения записывает `selected_visual_id` в задачу. При публикации выбранное изображение становится частью публичной карточки; остальные варианты остаются приватными.
- Содержимое изображения выдаётся отдельным защищённым маршрутом. В JSON каталога не класть base64. Для выбранного изображения опубликованной задачи допускается публичное чтение. Для черновиков — проверка владельца и при чтении метаданных, и при чтении байтов; не наследовать известную проблему доступа к черновикам по ID из `KNOWN_ISSUES.md`.

Минимальные метаданные: ID, задача, версия/хеш исходника, родительская версия изображения, статус (`queued/generating/ready/failed`), описание, MIME, местоположение байтов, дата, модель, выбранность. Состояние и изображение должны переживать reload; на перезапуске зависшее задание завершается понятным состоянием. Нужен ограниченный параллелизм и защита от повторной оплаты за одинаковое нажатие в пределах приложения. При неясном сетевом результате нельзя слепо повторять платный вызов.

По read-only проверке кода: отдельный интерфейс `ImageGenerator` позволит не менять общий `ai.Client` и его `fakeAI` в существующих тестах. `callWith` текущего текстового клиента ожидает структурированный текст; для изображения нужен отдельный разбор ответа. Точки фронтенда — `AgentChat/types.ts`, `transport.ts` и `AgentChat.tsx`. Сейчас завершение диалога сохраняет ответы и ведёт в редактор; для артефакта в чате потребуется отделить сохранение карточки от навигации. Генерировать следует из сохранённого согласованного набора полей/выбранного результата, не из неполного старого `card_preview`. Владельцы этих файлов уже ведут параллельную работу; интеграцию координировать через Абылая.

Ключ OpenAI остаётся на сервере. Ошибка/квота/отсутствие доступа не ломают текстовую карточку. Не выдавать за реальную генерацию заранее заготовленную картинку; демонстрационный fallback при необходимости подписывается. Размер и качество регулируются без изменения основного текстового AI-клиента. Фактические latency/usage измеряются после интеграции; обещания «мгновенно» не добавляются.

## Приёмка

1. Один выбранный результат создаёт через настоящий API один визуальный артефакт в чате; модель/usage/время зафиксированы без секретов.
2. Обычная реплика с правкой обновляет соответствующее текстовое требование и следующую версию изображения. Неизвестные факты не добавляются.
3. Reload сохраняет готовый результат и выбор; двойное нажатие не создаёт два задания; устаревший ответ не затирает свежий.
4. Ошибка API позволяет повторить или продолжить без изображения. Обязательный путь ТЗ доступен независимо от генерации.
5. Изображение не меняет баллы само; публикация происходит только после действия бизнеса; чужой черновик и его изображения недоступны.
6. Команда открывает опубликованную карточку и видит согласованный текст с критериями и выбранный концепт. Изображение не объявляется работающим прототипом.
