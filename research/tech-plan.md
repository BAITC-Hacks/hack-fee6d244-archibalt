## Минимальная архитектура

Один процесс Python 3.12: FastAPI для серверных форм и маршрутов, Jinja для HTML, CSS без сборки, `sqlite3` для хранения. Один `requirements.txt`, запуск `python -m app`; Docker и второй путь запуска делать только после проверки основного. Без регистрации: явный переключатель демонстрационной роли «Бизнес / Команда» и выбор одного из пяти синтетических профилей. Ни одна роль не назначает команду автоматически.

В `app/ai.py` единственная граница внешнего сервиса: из сырого текста и отрасли получить структурированные пробелы и не меньше трёх вопросов; при желании из текста и ответов получить **предложение** полей карточки. OpenAI Responses API используется только при заданном `OPENAI_API_KEY`. В отсутствие ключа, ошибке сети, тайм-ауте, неправильном JSON или нарушении схемы работает локальный детерминированный генератор вопросов по незаполненным полям. Он должен учитывать вход и показывать не меньше трёх релевантных вопросов, а не возвращать одинаковый текст для всех задач. Промпт, схема входа/выхода, пример и правило fallback документируются; в UI видно, был ли результат получен от API или локального режима. **AI не считает баллы и не публикует карточку.**

Для защиты от выдуманных фактов в запросе явно требуется `null` для отсутствующих сведений. Вывод проходит проверку схемы и попадает только в редактируемый черновик. Бизнес проверяет каждое поле и нажимает «Подтвердить» перед начислением баллов/публикацией. Предложенная в `PLAN.md` проверка пересечения слов может быть дополнительным сигналом, но сама по себе не доказывает отсутствие галлюцинации: перефразирование даёт ложный отказ, а случайное совпадение слов — ложный допуск. Если времени мало, безопаснее оставить неизвестные поля пустыми и формировать карточку из явно введённых ответов, чем автоматом заполнять догадками.

## Данные и границы экранов

Минимальная схема SQLite:

| Сущность | Поля, важные для пути |
| --- | --- |
| `tasks` | `id`, `industry`, `raw_text`, `status` (`draft`/`published`), десять полей карточки из ТЗ, `confirmed_at`, `score`, `created_at`, `updated_at` |
| `clarifications` | `task_id`, `field_key`, `question`, `answer`, `source` (`openai`/`local`) |
| `teams` | `id`, `name`, `interests`, `skills`, `technologies` |
| `proposals` | `id`, `task_id`, `team_id`, `idea`, `plan`, `eta`, `prototype_url`, `decision` (`pending`/`selected`/`rejected`), `created_at` |

`score` в БД — кеш результата единственной функции `rating.py`, обновляется **только при подтверждении версии карточки**. Черновые правки можно предварительно оценить в редакторе как «возможный балл», но каталог сортируется по подтверждённому баллу. Для опубликованной задачи подтверждение дополнения обновляет балл и место в каталоге. Нельзя делать ограничение `UNIQUE(task_id, team_id)` на отклики: ТЗ не ограничивает их число. Решение каждой заявки отдельно позволяет 0, 1 или несколько выбранных команд; «отклонить все» — последовательное ручное решение бизнеса.

Границы маршрутов/экранов: `GET /` — общий каталог `score DESC, published_at ASC, id ASC` плюс фильтры отрасли и уровня; `GET/POST /task/new` — сырой ввод; `GET/POST /task/{id}/clarify` — ≥3 вопроса и ответы; `GET/POST /task/{id}/edit` — десять редактируемых полей, breakdown, пробелы, отдельные действия «Сохранить» и «Подтвердить»; `POST /task/{id}/publish` — публикация подтверждённой версии, включая низкий балл; `GET /task/{id}` — карточка и предложения; `POST /task/{id}/proposals` — неограниченный отклик; `POST /proposals/{id}/decision` — ручной `selected`/`rejected`. Между `main.py` и шаблонами в первые минуты согласовать имена параметров `task`, `breakdown`, `missing`, `questions`, `proposals`, `teams`, `filters`, `actor` в `app/templates/CONTRACT.md`; владелец backend пишет, владелец UI подтверждает.

Формула рейтинга одна, детерминированная, семь групп из `TASK.md`: контекст+потребность 20; данные 20; ожидаемый результат 15; измеримые критерии 15; ограничения 10; пользователи 10; контакт+формат взаимодействия 10. Сумма — 100. Внутри группы фиксировать явные проверки и частичный балл, затем в README дословно объяснить их. Простая длина текста не должна автоматически давать максимум: например, критерии успеха требуют наблюдаемого признака, связь — контакт и способ общения. Разбивка, советы и итог должны вычисляться одной функцией. Уровни 0–39/40–69/70–89/90–100; низкий рейтинг не скрывает публикацию и не блокирует отклик.

## Воспроизводимые данные и запуск

При отсутствии набора организаторов подготовить четыре файла `seed/*.json`, в каждом минимум пять объектов: (1) черновики разных отраслей и полноты, (2) карточки со всеми полями и текущим баллом, (3) команды с интересами/навыками/технологиями, (4) предложения с идеей/планом/сроком/ссылкой. Баллы seeded карточек лучше пересчитывать кодом при импорте и проверять расхождение с указанным баллом. Загрузка идемпотентна; пустая локальная БД создаётся на старте. README описывает установку Python, установку зависимостей, одну команду запуска, URL, режим без ключа, необязательный `OPENAI_API_KEY`, сброс демо-данных, архитектуру, формулу, правила каталога и один 5-минутный сценарий. Ни личный аккаунт, ни API-ключ для основного демо не нужны.

Рекомендации командам, очки за последующий этап, `/teams` и Docker не должны блокировать сквозной сценарий; шаг о прогрессе из ТЗ можно описать как ограничение MVP, поскольку раздел 7 разрешает для демо остановиться на отклике и решении бизнеса.

**Главный технический риск:** контракт `main.py` ↔ Jinja и последовательность подтверждение/оценка/публикация разойдутся при параллельной работе, и даже готовые модули не дадут сквозной демонстрации. Запасной путь: один серверный маршрут за другим, общий `CONTRACT.md`, локальный AI как режим по умолчанию, один заранее подготовленный сценарий и интеграционная проверка каждого перехода сразу после слияния. При срыве срока убрать вторичные страницы, но сохранить все обязательные действия на двух ролях.
