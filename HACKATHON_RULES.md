## Жёсткие требования (нарушение = дисквалификация или недопуск)

1. **Вся разработка только в этом репозитории** (`BAITC-Hacks/hack-fee6d244-archibalt`). Никаких сторонних/закрытых репо.
2. **Каждый час — видимый прогресс в репо.** Коммитить часто и осмысленно: код, прототип, схема, тесты, данные. Пустой час = основание для дисквалификации (п. 5.4.8, 5.9.2).
3. **Основная функциональность создаётся во время соревновательной части.** Заготовки, шаблоны, библиотеки — можно, но готовый продукт до 13:00 — нельзя (п. 5.4.4.2, 5.4.5).
4. **Раскрывать все сторонние компоненты**: open-source библиотеки, модели, датасеты, шаблоны, чужой код. Вести список в README (п. 5.4.4). Скрытое использование чужого решения = дисквалификация.
5. **Проект должен запускаться экспертом самостоятельно по README.** Если не запустился — команда выбывает, пояснения не принимаются (п. 5.4.16, 5.6.5).
6. **Проверка без личных аккаунтов участников.** Внешние API/сервисы → предоставить тестовые ключи, демо-доступы или mock-режим (п. 5.6.6).
7. Никакого вредоносного кода, попыток доступа к чужим системам, вмешательства в платформы (п. 5.9.2).
8. AI-инструменты и агенты разрешены без ограничений (п. 5.4.12).

## Обязательное содержимое README (п. 5.4.15)

README должен содержать все пункты, иначе техпроверка не пройдёт:

- [ ] Описание решения и его назначения
- [ ] Описание архитектуры
- [ ] Используемые технологии
- [ ] Инструкции по установке
- [ ] Инструкции по запуску
- [ ] Необходимые зависимости
- [ ] Параметры окружения (переменные, `.env.example`)
- [ ] Порядок проверки основного сценария работы (пошагово, что нажать/вызвать и что должно получиться)
- [ ] Список сторонних компонентов и их лицензий

Цель: эксперт, который не видел проект, разворачивает и проверяет его сам, за минимальное число шагов.

## Практические выводы для агентов

- **Работающий end-to-end сценарий важнее ширины фич.** Один сценарий, который стабильно демонстрируется, бьёт пять полуготовых.
- **README пишется параллельно с кодом**, не в конце. Проверять, что он актуален, перед каждым крупным коммитом.
- **Запуск в одну команду** (`docker compose up`, `make run`, или один скрипт). Без ручной магии.
- **Все секреты — через `.env`**, в репо `.env.example` с заглушками и тестовыми ключами/mock-режимом.
- **Коммиты минимум раз в час**, лучше чаще. Сообщения на русском, в императиве, по сути.
- **Никаких артефактов после 18:00** — в 17:45 фиксировать финальное состояние, проверить README, запушить.

## Контекст конкуренции

2500 участников, 10 призовых мест, единый зачёт. Жюри и AI-судья видят сотни проектов.
Идея, польза и результат должны считываться **за 30 секунд** — из README, из первого экрана, из ролика. Если нужно объяснять, значит не сработало.

## Жюри-ревью (обязательная процедура)

Запускается в две точки, не чаще:
1. **На первой мысли** — до написания кода, по описанию идеи (1 абзац + сценарий демо).
2. **После реализации** — по коду, README и сценарию ролика.

Состав: главный агент (Fable, оркестратор) + 3 агента-жюри (Opus), каждый со своей ролью:
- **Инвестор/бизнес** — ценность, потенциал масштабирования, кто платит.
- **Технический эксперт** — запускается ли по README, реально ли работает сценарий, честность заявленного.
- **Пользователь/UX** — понятно ли с ходу, что это и зачем; смотрит как зритель ролика.

Каждый жюри ставит баллы по критериям Demo Day (см. таблицу выше) и даёт до 3 замечаний, ранжированных по влиянию на балл.
Оркестратор сводит замечания, отбрасывает противоречащие друг другу и мелкие, исправляет существенные, запускает следующую итерацию.
Стоп: ни одного замечания с потерей ≥5 баллов, либо 3 итерации.

Вызов: `/jury-review idea` или `/jury-review code`.
