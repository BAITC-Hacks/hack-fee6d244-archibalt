## Внутреннее жюри-ревью

### Когда

Две стадии:
1. **Идея** — до кода, по описанию: 1 абзац + сценарий демо на 60 секунд. Один или несколько прогонов, пока идея не доработана.
2. **Готовое решение** — по коду, README, сценарию ролика. Повторные прогоны внутри стадии разрешены и ожидаются: после каждого блока правок — новый прогон. Финальная проверка — **три независимых прогона** с чистым контекстом у каждого жюри; расхождения между прогонами — сигнал нестабильности, разбирать.

### Кто

Роли и процедура — по `JUDGE_AGENT_PROMPT.md`. Оркестратор выполняет роль **Jury Chair**: собирает материал, запускает четыре независимых персоны отдельными процессами с изолированным контекстом, сводит вердикты, вносит правки. Персоны:
- **Gatekeeper** — видит только название, one-liner, первый экран и первые 10 секунд демо. `PASS`/`SKIP`.
- **Product Judge** — проблема, соответствие Education-кейсу, образовательный эффект, ясность, отличие от чата, внедрение.
- **Technical Judge** — agentic-поведение, OpenAI API, работоспособность end-to-end, надёжность, безопасность, честность демо. На стадии «готовое решение» реально запускает проект по README; не запустилось — стоп. Отдельной строкой — чеклист техотбора (README по п. 5.4.15, допуск, ТЗ), не смешивая с баллами.
- **Red Team Judge** — минимум пять оснований отклонить проект.

Модель — только Opus 5.5 для персон, Fable 5.1 для Chair. Независимость важнее конкретной модели.

Судьи получают только то, что увидит реальное жюри: без внутренних намерений команды. Формат ответа — по разделу «Формат ответа» в `JUDGE_AGENT_PROMPT.md`.

### Условия остановки и статусы

Release gate — по `HACKATHON_STRATEGY.md`: цель **100/100 по каждому критерию** официальной рубрики, три независимых blind review подряд, Gatekeeper `PASS`, у Red Team нет нерешённых причин. Итерация повторяется, пока хотя бы один критерий ниже 100 **и** у жюри есть конкретное исполнимое замечание.

Статусы: `READY TO SUBMIT` только при валидных 100/100 по **официальной** рубрике; без официальной рубрики итог всегда `PROVISIONAL — NOT READY`; ниже 100 — `NOT READY` с точным списком недостающих доказательств. Какая рубрика официальна для какого этапа — см. «Два разных этапа оценки»: для Demo Day она есть (п. 5.7.2), для техотбора — ТЗ ещё не получено.

**Балл всегда честный, завышать запрещено.** Если критерий ниже 100, а конкретной правки жюри не нашло — вывод фиксируется как «ниже 100, способ улучшения пока не найден» с перечислением недостающих доказательств (чего не хватает, чтобы поставить выше). Код-фриз и дедлайн останавливают работу, но не превращают оценку в 100/100: в отчёте остаётся фактический балл и список нерешённых проблем, решение об отправке принимает команда.

Ограничение по времени (см. следующий раздел) останавливает итерации, но не отменяет цель и не меняет балл.

## Работа в дуо (два человека в одном репо)

Второй участник параллельно работает в этом же репозитории. Не ломать его работу.

Перед любым изменением:
1. `git fetch && git status -sb` — понять, что изменилось на `origin/main` и есть ли расхождение.
2. `git pull --rebase` — подтянуть чужие коммиты до своих правок. Конфликт — разбирать руками, не выбирать «свою» версию вслепую.
3. `git log --oneline origin/main -5` и `git diff HEAD origin/main --stat` — какие файлы трогает напарник.

Во время работы:
- Не редактировать файлы, которые напарник менял в последних коммитах, без явной договорённости. Свою часть держать в отдельных папках/модулях.
- Не трогать чужие ветки, не удалять чужие файлы, не переименовывать общие модули.
- Коммиты мелкие и частые: один смысл — один коммит. Пушить сразу после коммита.

Запрещено:
- `git push --force`, `git reset --hard origin/...`, `git rebase` уже запушенных коммитов, `git checkout -- .` без проверки, что там нет чужих правок.
- `git add -A` вслепую — сначала `git status`, добавлять только свои файлы.
- Переписывать историю и удалять чужие коммиты.

После пуша: `git log --oneline origin/main -3` — убедиться, что коммит ушёл и напарника не затёрло.
