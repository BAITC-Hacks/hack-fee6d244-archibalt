## Внутреннее жюри-ревью

### Когда

Две стадии:
1. **Идея** — до кода, по описанию: 1 абзац + сценарий демо на 60 секунд. Один или несколько прогонов, пока идея не доработана.
2. **Готовое решение** — по коду, README, сценарию ролика. Повторные прогоны внутри стадии разрешены и ожидаются: после каждого блока правок — новый прогон. Финальная проверка — **три независимых прогона** с чистым контекстом у каждого жюри; расхождения между прогонами — сигнал нестабильности, разбирать.

### Кто

- **Оркестратор** — агент, который собирает материал, запускает жюри, сводит замечания, вносит правки.
- **Три агента-жюри**, каждый запускается отдельным процессом с изолированным контекстом (не видит ответов других жюри и переписки оркестратора). Модель — любая доступная в среде; независимость важнее конкретной модели. Роли:
  - **Инвестор/бизнес** — ценность (25), потенциал (20). Кто платит, почему это не сделали до нас.
  - **Технический эксперт** — результат и качество (20), инновационность (15). На стадии «готовое решение» реально запускает проект по README; не запустилось — стоп, остальное не оценивается. Отдельно проверяет чеклист техотбора (README, допуск, ТЗ) и отчитывается по нему **отдельной строкой**, не смешивая с баллами Demo Day.
  - **Пользователь/зритель** — презентация и ясность (20). Проверяет пороги 10 и 30 секунд как зритель ролика и читатель README.

Промпты жюри — в `JUDGE_AGENT_PROMPT.md` (у напарника). Формат ответа каждого: баллы по своим критериям, до 3 замечаний вида `[-N баллов] проблема → что сделать`.

## Работа в дуо (два человека в одном репо)

Второй участник параллельно работает в этом же репозитории. Не ломать его работу.

Перед любым изменением:
1. `git fetch && git status -sb` — понять, что изменилось на `origin/main` и есть ли расхождение.
2. `git pull --rebase` — подтянуть чужие коммиты до своих правок. Конфликт — разбирать руками, не выбирать «свою» версию вслепую.
3. `git log --oneline origin/main -5` и `git diff HEAD origin/main --stat` — какие файлы трогает напарник.

Во время работы:
- Не редактировать файлы, которые напарник менял в последних коммитах, без явной договорённости. Свою часть держать в отдельных папках/модулях.
- Не трогать чужие ветки, не удалять чужие файлы, не переименовывать общие модули.
- Коммиты мелкие и частые: один смысл — один коммит. Пушить сразу после коммита.

Запрещено:
- `git push --force`, `git reset --hard origin/...`, `git rebase` уже запушенных коммитов, `git checkout -- .` без проверки, что там нет чужих правок.
- `git add -A` вслепую — сначала `git status`, добавлять только свои файлы.
- Переписывать историю и удалять чужие коммиты.

После пуша: `git log --oneline origin/main -3` — убедиться, что коммит ушёл и напарника не затёрло.
